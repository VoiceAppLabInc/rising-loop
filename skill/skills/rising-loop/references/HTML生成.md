```
  L02.html

  project.css    このプロジェクト独自の CSS（無くてもよい。「合わせて」で上書きされない）
  rising.js      共通 JS。assets/ からそのままコピー
```

**1ループ1ファイル**なのは、1件扱うのに1ファイル読めば済むから。全部を1枚に入れると、1件直すのに全部読むことになる。

### `loops/README.md`

**このスキルがプロジェクト非依存でいられるための鍵。** ここに書いてあるコマンドを読んで実行する。

```markdown
# loops — このプロジェクトの運営ループ

> 各ループの正は `loops/LXX.html`（`LOOP_DATA` が値の正）、出来事は `loops/logs/*.md` が正。
> 運用は `/rising-loop`。

## 数字の取り方

**このプロジェクトで数字をどう取るかを、実行できる形で書く。** rising-loop は毎回ここを読む。
書き方の例:

アクセス解析  <そのまま実行できるコマンド>
              ⚠ 反映の遅れがあるなら、その時間と、直近を見る代わりの方法
DB            <そのまま実行できるコマンド。絞り込み条件も書く>
売上          <台帳の場所と見方>

売上       LINEコンソール（手で入れる）

## 数字を見るときの注意

- staging と本番が同じGA4プロパティにいる。`stage` で必ず絞る
- 〇〇は計測していないので、この数字には出てこない
```

⛔ **セッションIDの表は置かない。** 右のチャットの ID はアプリ側が持つ（昔の `loops/.chat-sessions` はアプリが読むだけ）。
README にも `index.html` にも写しを持たせない（写しがあると必ず食い違う）。

**数字が手入力のプロジェクトなら「手で入れる」と書いておく。** そうすればスキルは聞きに来る。

## 3つのファイル

**1枚に全部を入れない。** 全ループの画面と共通の CSS/JS を1ファイルに入れると、ループごとの子が同じファイルを同時に直せず、共通部品の差し替えも中身と混ざる。
それでも **画面を切り替えても右のチャットが切れない**ことは崩さない（右のチャットはアプリが持ち、頁は iframe 1枚で出す）。

### 殻（`index.html`）

持つものは6つ。**ループの中身は持たない。**

- **一覧** `<section class="screen" id="s-list">`（行・ゲージ・ステータス・合算の数字ブロック `.rev`）
- 版の表示 `<span class="ver" hidden>`（見えない。アプリが版の判定に使う）
- ループ表示の枠 `<iframe id="loop-frame">`
- **2つのマーカー**（「合わせて」で残す場所・一覧の更新で直す場所）

```html
<!-- CONST:BEGIN -->  PROJECT_DIR / SERVICE_NAME / PANES     <!-- CONST:END -->
<!-- LOOPS:BEGIN -->  一覧（合算の数字ブロック .rev と行）   <!-- LOOPS:END -->
```

- **値は CONST ブロックだけに置く。** `<title>`・見出しのサービス名は `rising.js` が、`PROJECT_DIR`・`PANES` はアプリがここから読む。**ベタ書きしない**（原理7）
- 画面の切り替えは `show()`。**頁を替えるときは `loop-frame` を新しく作り直す**（`src` を付けた iframe を作ってから `replaceWith` で差し込む）。⚠️ 同じ iframe の中身を差し替えない（`location.replace` も `iframe.src = …` も）——ブラウザの履歴が殻の hash と iframe の中身を一緒に覚え、戻る・進むで iframe だけ昔の頁に戻されて hash とずれる（★ 2.3.2 で直した。一覧 → A → 一覧 → B → 一覧 → A から戻ると、一覧が続いたり1つずれたりした）。⚠️ 差し込んだあとに `src` を付けない（Safari は about:blank → 頁 を履歴に積む。★ 2026-09-17 の検証で実際に起きた）
- **履歴は殻の hash だけが持つ**（`index.html#s-list` / `#s-L01`）。`hashchange` のリスナを増やさない。同じ id なら再読込しない
- `loop-frame` は縦いっぱい・中スクロール。**対象はアプリの中の Chromium**。印刷は対象外（必要なら `LXX.html` を単体で開く）

**頁から来るメッセージを受ける**（`postMessage`）。何を聞くか・指示文の組み立て・アプリへの受け渡しは**全部 殻がやる**（入力の窓と右の窓はアプリが出す）。

| 頁 → 殻 | 中身 | 殻の動き |
|---|---|---|
| `{t:'go', id}` | 移動先の画面ID（`s-list` / `s-LXX`） | `show(id)` |
| `{t:'copy', kind, d}` | `kind` は `upd` / `copy`、`d` は押されたボタンの**生の `data-*`** | `upd` は文を入れた入力の窓を `rlaApp.ask` で出し、［送る］で `rlaApp.send`（`copy` はクリップボード） |
| `{t:'modal', kind, d}` | `kind` は `add-loop` / `ins` / `do` / `cmt`、`d` は押されたボタンの**生の `data-*`** | 殻が `rlaApp.ask` でアプリの入力の窓を出し、答えで `block()` を組んで `rlaApp.send` |

**chips（定型の札）・文言・`block()` の組み立ては、すべて殻に一本化する。頁は生の `data-*` を送るだけ。**

- ⛔ `targetOrigin` は **`'*'` 一択**。Safari は file:// を毎回別のオリジンにするので `'/'` も `'null'` も使えない
- **送信元の検証は `event.source === loopFrame.contentWindow`（殻）／`event.source === window.parent`（頁）。`event.origin` は見ない**
- `.cmt` の `data-sec` を見出しの語に加工する処理（`kickOf` と `「…」` の抜き出し）は**殻に残す**。頁は生の `data-*` をそのまま送る
- `compose` は殻に1つ（`block(loop, section, target, v, key)`）。頁からは生の `data-*` だけ渡す。**用途が増えても分岐が増えない**

### ループ頁（`LXX.html`）

そのループ1つぶんの画面と、そのループのグラフのデータだけ。

- `<html lang="ja" data-page-schema="2" data-loop-ver="2.0.0">`。
  - `data-loop-ver` は、この頁が**どの版の作りか**の印（台帳 `migrations.json` の項目をどこまで反映したか）。新しく作るときは雛形のまま残す。版を上げる作り直しで台帳の項目を反映したら、その版に書き換える。アプリはこの印で、まだ作り直していない頁を見分ける
  - `data-page-schema` は値の持ち方の連番（1.5.0 で 2 になった）。いまは変えない
- 読むものは3つ: `rising.css` / D3（**UMD 版を `<script src>` で**。`type="module"` と `fetch('./*.json')` は file:// で使えない）/ `rising.js`
- 中身は `<section class="screen" id="s-LXX">` **1つだけ**。上に `← ループ一覧`（`data-go=""`。行き先は空にする。`s-list` にすると殻のアドレスが `#s-list` になり、ブラウザが一覧の枠まで送って少し下にずれる）
- 値は `var LOOP_DATA = {…}` の1か所（下の「`LOOP_DATA` の定義」）。**ループIDで引く形にしない**（頁にはそのループしか無い）
- ⛔ **入力の窓・右の窓を持たない。** ボタンは押された事実を**殻に `postMessage` するだけ**
- ⛔ **`navigator.clipboard` と `localStorage` を頁で使わない。** iframe の中では拒否される環境がある。指示文を組むのも記憶も殻がやる（殻が `rlaApp.send` でアプリに渡し、アプリが右のチャットへ送る）
- **単体で開いたとき**（`window.parent === window`）は、上に1行「この頁は `index.html` から開いてください」とリンクを出し、ボタンは押しても何もしない。**壊れないことだけ保証する**

## `LOOP_DATA` の定義

**`data-page-schema="2"` の頁が持つ形。値の正はここ。散文の中の数字はここから写す。**

```js
var LOOP_DATA = {
  id: "L01", parent: null,
  title: "ホスト1人あたりの券の手取りを 24円 に",
  summary: "券は売れているが買い手が10人から増えていない",      // 一覧の .loop-sub に写す。60字以内
  updated: "2026-09-17",
  metric: {
    name: "…",                                                   // 数字の名前
    start: 3.46,                                                 // はじめた頃の値
    measured: "2026-09-17",                                      // この数字を取った日
    window: "2026-09-11〜2026-09-17（今日を含む直近7日…）"        // 窓の説明
  },
  //  ★ now / target / unit / unit_price は metric に持たない。now は hist.points[] の最新値、
  //    target・unit・price は hist.target / hist.unit / hist.price が正（同じ値を2か所に置かない）
  hist: { …unit / price / target / targetLabel / dayUnit / dayTarget / dayTargetUnit / dualAxis / days[] / line[] / points[] / after[]… },
  funnel: { …stages[] / note… },
  trials: [                                                      // いま動かしているもの
    { id: "T06", title: "…", status: "実現方法を決めるところ",
      plan: ["⬜ 1. 実現方法を決める", "⬜ 2. …"] }
  ],
  records: [                                                     // RECORD の値の部分
    { id: "T04", title: "…", done: "2026-09-13",                 // 実施日
      summary: "券を3種類にした",                                // 変更の要旨
      aim: "高い券を選ぶ人を出す",                                // 狙い
      before: "窓 9/2〜9/8: 9件・1,530円",                        // 実施前の数字と比較条件
      forecast: "2週間で 7件 → 10件", forecast_at: "2026-09-13",  // 予想と、予想を書いた日
      judge: "2026-09-27",                                        // 判定日
      grade: "C", graded: "2026-09-17",                           // 現在の評価と評価日。未評価は "-"
      verdict: null, verdict_at: null, verdict_by: null }         // 確定判定（効いた／わからなかった／効かなかった／逆効果）・日・誰が
  ]
};
```

- `hist.points[]` が履歴の正。**「いま」の値はその最新点**。`metric` に `now` を持たない。`points[]` は `at` / `value` / `note` / `recs` を持つ。別配列にしない
- `days[]` には日ごとの表にしかない列（例: `hosts`）を足してよい。**派生値（単価での復元など）は持たない**
- `records[]` は `SKILL.md`「RECORD」の「保持するもの」（実施日・変更の要旨・狙いと予想・実施前の数字と比較条件）と「更新するもの」のうち値で持てるもの（評価・評価日・確定判定）。**評価文・根拠・限界・観測表の散文は `.record-item` の markup に書く**
- **`rising.js` が読むのは `hist` と `funnel` だけ**（`data-goal-now/when/fill/diff/money` を埋める）。`start` `target` `unit` の表示は markup 直書き。★ **`trials[]` `records[]` は AI が読む正で、JS は使わない**
- 無い項目は `null`。省略しない
- コメント（`//===`）は既存の1組だけ。**定義の変更履歴を増やさない**（原理6）。経緯は `logs/` へ

## 写しの規則

- 写しの規則は **`metric` ／ `hist.days` `hist.line` `hist.points` ／ `funnel` の値**に限る。ゴール下の一文・一覧の行・グラフ注記に出るこれらの数字は、`LOOP_DATA` と同じ値であること。更新のたびに「**この数字は、いまの `LOOP_DATA` の値か**」で見直す
- ⚠️ **派生値（割合・倍率・差分）と RECORD 内の観測表の数字は markup が正。突き合わせの対象外**（L01 の本文には約330個の数字があり、`LOOP_DATA` に対応があるのは約70個。残りを全部持たせると `records[]` が本文と同じ大きさになる）
- `data-goal-now/when/fill/diff/money` と `data-hist` `data-funnel` は `rising.js` が `LOOP_DATA` から埋める
- **突き合わせは頁の中**（散文の数字 ⇄ `LOOP_DATA`）。ファイル間ではない

### 共通（`rising.css` `rising.js`）

- **`assets/` のものを、そのまま `loops/` にコピーする。値を埋めない**（原理7: 規則はスキルに、値はループに）
- 「このループを合わせて」では**ファイルごと上書き**される。**プロジェクト側で書き換えない**（書き換えても次の「合わせて」で消える）

### `loops/update/` — ループごとの更新スクリプト

「更新」で `LOOP_DATA` の値を書く計算は、同じループなら毎回同じ。**AI が初回の更新で Python に残し、次回からは親が実行するだけ**にする（`SKILL.md`「数字を更新し、施策を再評価する」手順 A/B）。

```
loops/update/
  common.py    スキルの assets/loopdata.py の写し。load / save / merge_days / add_point。アプリの［新しい形にする］で上書きされる。★プロジェクト側で書き換えない
  L01.py       L01 の計算。README のコマンドを subprocess で叩き、LOOP_DATA の値（days[] line[] points[] metric updated）を書き換える。★このプロジェクトのもの。「合わせて」は触らない
```

- `LXX.py` の中身は自由（python3 標準ライブラリのみ）。決まっているのは入口と出口だけ: `d = load('loops/LXX.html')` で dict、値を直して `save('loops/LXX.html', d, dry_run=…)`。使い方の例は `common.py` の先頭にある
- `save` は**値だけ**を元の位置に書き戻す。`//===` コメント・キーの並び・数値の桁・`LOOP_DATA` の外（`data-page-schema`・markup）は変えない。書く前に `loops/.tmp/LXX-before-update.html` に退避し、差分の表を出す。`--dry-run`（`dry_run=True`）は表だけ
- `save` が書くのは値。**`summary`・`points[].note`・散文・評価文は子が書く**（`LOOP_DATA` の値は触らせない）
- ★ **`LOOP_DATA` の計算（窓・分母・単価）を変えたら `update/LXX.py` も直す。** 片方だけ直すと次回ずれる
- スクリプトが失敗した回（出力の形が変わった・コマンドが無い）は初回扱い。子が更新し、スクリプトも直す
- `cwd` はプロジェクトの根（`python3 loops/update/LXX.py`）。README のコマンドがその前提で書かれている
- 実行すると `loops/update/__pycache__/` ができる。正ではない。消してよいし、git に入れない

## 作るとき

1. 殻 ← `../assets/index.html` をコピーし、**CONST ブロック**（`PROJECT_DIR` `SERVICE_NAME` `PANES`）を埋め、**LOOPS ブロック**の一覧をループのぶんだけ書く
2. ループ頁 ← ループごとに `../assets/loop.html` をコピーして `LXX.html` に。`id="s-LXX"` と `LOOP_DATA` を埋め、散文をその値に合わせて書く
3. 共通 ← `../assets/rising.css` `../assets/rising.js` をそのままコピー

⚠️ 雛形の中身は**形式を見せるための架空例**。**構造だけ借りて、文章と数字は必ず置き換える。**
⚠️ `PROJECT_DIR` を雛形のプレースホルダ（`'/絶対パス/プロジェクト'`）のまま置かない。

殻と各頁の先頭にこれを残す。

```html
<!-- このファイルが、このループの正です。値は下の LOOP_DATA、散文はその写しです。
     数字を変えるときは LOOP_DATA から直して、同じターンで散文も合わせてください。 -->
```

殻には代わりにこれを残す。

```html
<!-- 一覧の行は各ループ頁の LOOP_DATA の写しです（残る二重はここだけ）。 -->
```

## 一覧の行（1.7.4）

`.loop-num` の中に書くのは**3つだけ**。

```html
<div class="loop-num"><b>433</b> / 3,300 人/日
  <div class="loop-delta"></div>
  <div class="rl rl-tight" data-rl='{"t":"bullet","unit":"人/日","max":3300,"now":433,"aim":3300,"was":248,"axis":false,"lg":false}'></div>
</div>
```

- `now` は最新の計測点、`aim` と `max` は目標、**`was` は `metric.start`（はじめた頃）**
- `.loop-delta` は**空のまま**。`rising.js` が「↑ はじめより +75%」を入れる
- **行の左の帯**（緑／赤）と**数字の色**も `rising.js` がブレットから決める。色の決まりはブレットと同じ
  （はじめより悪くなっていたら赤）

★ **百分率と色を自分で書かない。** AI が計算すると間違えるうえ、色の決まりが2か所に分かれる。
値を1行書けば、帯・数字・差分・ブレットが同じ決まりで揃う。

★ **背景は塗らない。** 下がっている行も背景は他と同じ。帯と数字だけが赤になる。
行ごと赤く塗ると一覧が重くなり、帯の意味が薄れる。

★ 上限の目標（サーバー代など）は `"aimLabel":"上限"` を足す。上がったときが赤になる。

★ 1.7.3 までの `<div class="loop-bar"><i style="width:13%"></i></div>` は**古い形**。
目盛りも向きも無く、6% と 13% がどちらも「ほぼ空」に見えた。一覧を直すときに書き換える。

## ループを追加

3か所。**どれか1つでも抜けると、開けない画面か、消えたループになる。**

1. `../assets/loop.html` から `LXX.html` を作る（`id="s-LXX"`・`LOOP_DATA`・散文）
2. 殻の **LOOPS ブロック**の一覧に、その行を足す（ゲージ・`.loop-sub`・`.state`。合算の `.rev` も見直す）
3. 殻の **CONST ブロック**の `PANES` に `'s-LXX'` を足す（チャットを付ける画面ID。足さないとそのループにチャットが付かない）

## 更新するとき

**全文を書き直さない。** 変わったところだけ差し替える。

| 何を直したか | どのファイル |
|---|---|
| そのループの数字・本文 | `loops/LXX.html`（**そのループの子が直接直す**。殻と他の頁は開かない）。**先に `LOOP_DATA`、次に散文**。`loops/update/LXX.py` があれば `LOOP_DATA` の値はそれが書き、子は散文だけ |

★ **差し替えたら、タグの開閉が揃っているか数える。見た目では気づけない。**
`</div>` が1つ余ると、そこで枠が閉じ、後ろの中身が枠の外にはみ出して**背景色が変わる**。
1つ足りなければ逆に、次の枠に巻き込まれる。

- 差し替えは**要素の開きタグから閉じタグまでを丸ごと**にする。
  「最初に見つかった `</div>` まで」のような検索の境界で切り出して、そこに自分でも閉じタグを書き足すと**二重**になる
- 直したら**同じターンで**下の検算を回し、全部の頁が揃っているのを見てから返す。ずれが出たら直るまで返さない

```bash
python3 - <<'EOF'
import re,io,glob
for f in sorted(glob.glob('loops/L*.html')) + ['loops/index.html']:
    s=io.open(f,encoding='utf-8').read()
    for m in re.finditer(r'<section class="screen" id="(s-[^"]+)">', s):
        a=m.start(); b=s.index('</section>', a); sec=s[a:b]   #=== 画面の </section> まで
        o=len(re.findall(r'<div\b',sec)); c=sec.count('</div>')
        print(f, m.group(1), o, c, '' if o==c else '★ ずれ')
EOF
```

★ 実際にやった（2026-09-10）。施策案の一覧を5件から4件に詰め直したとき、検索で「最初の `</div>` まで」を切り出し、
そこに自分でも `</div>` を書き足して閉じタグが二重になった。ボトルネックの枠がそこで閉じ、TRIAL 以降がはみ出して背景が変わった。
ユーザーの反応は「**あれ、背景色がおかしくなってるぞ**」「**そういうことがないように skill に明記しろよ**」。

★ **`LOOP_DATA` を直したら、同じターンで散文も直す。例外なし。**

  **古い結論を読ませることになる**

★ **1つのループを直したら、必ず殻の一覧（`#s-list`）も見る。同じターンで直す。**

## ★ 入力は受けない

**HTMLは見る専用。操作はチャット。** HTMLが入力を受けると、正が2つになる。

ボタンは全部、**指示文を作ってアプリに渡す**（`rlaApp.send`）。アプリがそれを受け取り、いま見えている画面の右のチャットに貼り付けて Enter まで押す。ユーザーはコピーも貼り付けもしない。

**プロジェクト独自の CSS は `loops/project.css`。** 殻もループ頁も `rising.css` の後に読む（無ければ無いでよい）。
`rising.css` は「合わせて」で丸ごと上書きされるので、画面固有の見た目（そのループだけの表・図・印）をそこに足さない。
分割（`split-index.py`）は元の `<style>` のうち `rising.css` に無い規則を自動で `project.css` に移す（★ 1.3.0 でこれを落とし、プレイルームの表が全部崩れた。2026-09-18）。

### 指示文の形

**先頭にループIDを、続けてループ名を置く。** 届いた指示文だけで場所が決まるようにするため。

**形式は YAML ブロック**（`block()` が組み立てる）。届くだけで、どのループのどこへの話かが決まる。

```
---
loop: L01
section: BOTTLENECK
target: ゲーム枠の上にロック解除ボタンを置く
rule: まず /rising-loop を呼び出して最新の手順を読み、それに従うこと
feedback: |
  ここに入力した本文
---
```

| ボタン | `section` | `target` | 本文のキー |
|---|---|---|---|
| ボトルネックの各行 `指示する` | `BOTTLENECK` | 施策案のテキスト | `feedback` |
| TRIAL の `指示する` | `TRIAL` | 施策名 | `feedback` |
| 各セクションの `コメント` | そのセクション（`GOAL` `REPORT` `BOTTLENECK` `TRIAL` `RECORD`） | 該当項目があれば | `feedback` |
| GOAL の `更新` / 一覧の `全ループ更新` | — | — | `task`（人の言葉ではなく命令なので） |
| 一覧の `ループを追加`（`.add-loop`） | `LOOPS` | — | `task`（`ループを追加して: <入力>`） |

★ **IDを先頭に置く理由。** 目標のタイトルは運用しているうちに言い換わる（「週20回に」→「週10件に」）が、
**IDは変わらない**。IDがあれば `loops/L01.html` へ直行できる。タイトルだけだと突き合わせが要る。

★ **画面にもIDを出す。** キッカーを `GOAL · L01` の形にする（`<span class="lid">· L01</span>`）。
ボタンを押さずに「**L01の3番やって**」と口で言えるようになる。

★ **番号だけでなく項目のテキストも入れる。** 送ってから AI が読むまでの間に項目が片付くと番号が繰り上がる。テキストがあれば取り違えない。

### ファネル（数字はここで落ちています）

**横向きのファネル。高さは値の対数**で、先細りがそのまま落ち方になる（`drawFunnel`）。
帯の中に前の段からの通過率、上下の余白が「ここまでに失った人」。

```html
<div class="funnel-f" data-funnel="L01"></div>
```

```js
//=== その頁の LOOP_DATA の中。ループIDで引く形にしない
funnel: {
  note: "帯の中の % は…",
  stages: [ { name: "起動", value: 593, unit: "人" }, … ]
}
```

- ⚠️ **高さを実数に比例させない。対数にする。** 先頭と末尾で桁が違うのが普通で
  （実例: 593 → 3 で約200倍）、実数だと**末尾が線になって消える**
- ⚠️ **段を横に並べた HTML（`.stage` と矢印を交互に置く形）に戻さない。**
  段が5つを超えると折り返して読めなくなる。実際にそうなって作り直した
- 単位が混ざるときは（人と件など）、`unit` を段ごとに持たせて注記に書く
- **D3 が読めなかったときは、段の名前と数字を文字で出す**（数字だけは必ず残す）

### ボトルネックの行

番号を振り、ホバーで `やる` が出る（タッチ端末では常時表示）。

```html
<div class="open-item active">
  <div class="dot">▶</div><div class="no">1</div>
  <div>ヘタウマの完走率が 29%。1試合に 21分半 かかっています</div>
  <button class="do" data-id="L01" data-loop="…" data-no="1" data-text="…">指示する</button>
</div>
```

TRIAL に拾い上げた案は、この一覧から**消す**（`SKILL.md` 原理1）。`▶` や `active` を付けて残さない。

★ **番号があるので、ボタンを押さず「L01の2番やって」と打っても通る。** ボタンは手間を減らす補助で、唯一の入口にしない。

### GOAL の履歴（計測日・折れ線・区間の記録）

数字の下に **`<日付> 時点の数字`** を出し、その下に履歴ブロックを置く。

```
8月30日 時点  40%                            診断した日（実質2日・559回）
──────────────────────── 目標 60%
             ●
 この計測までに入ったこと
  8/30  6人以上は26回やって完走ゼロ…
 この計測のあとに入ったこと（次の計測で判定に使う）
  9/1   どこで抜けているかの計測を入れた…
```

- データは頁の `<script>` の `LOOP_DATA.hist.points[]` に持つ（**ここが履歴の正**。出来事 `recs` は `loops/logs/<ID>.md` から最近の数件を写す）
- 折れ線は **D3 で実寸に描く**（`drawChart`）。ファネルと同じ道具に揃えている
- ⚠️ **`viewBox` で横に引き伸ばさない。** 伸ばすと点の丸が楕円に歪み、
  目標のラベルを HTML で重ねる回避策が必要になる。実寸なら `<text>` をそのまま置ける
- ⚠️ **何の線か分からない破線を置かない。** 目標線には必ずラベルを付ける
- ⚠️ 注意書きは `innerHTML` の中に入れる。`insertAdjacentHTML` で足すと**再描画のたびに増える**
- 記録は **「前の計測 〜 この計測」の区間**だけ。最新の点のときだけ、
  **「この計測のあとに入ったこと」**を続けて出す（次の判定で汚染を疑う材料になる）

### ★ 折れ線だけにしない。日ごとの棒を下敷きに敷く

**計測点の折れ線だけだと読めない。** 縦軸が 0〜目標なので、44 → 37 → 37 → 39 のような
実際の動きが潰れて**ただの水平線に見える**。しかも点は数日に1つしか増えないので、
**線が線になるまで何週間もかかる**。

★ **折れ線は数日に1点しか増えないので、それだけでは動きが読めない。** 日ごとの棒を下敷きに敷く。

```
──────────────────────── 目標 60%
   ●─●─●─●─●─●─●─●        ← 折れ線＝その日に計測していたらいくつだったか（line）
  ███ ███ ███ ███ ███ ███   ← 棒＝その日の値（days）
  43% 35% 34% 42% 38% 38%
  8/29 8/30 8/31 9/1 9/2 9/3
```

★ **折れ線は「その日に計測していたらいくつだったか」を日ごとに描く**（`LOOP_DATA.hist` の `line`）。
計測点だけをつなぐと**数日に1点しか増えず、線がほぼ水平のまま**になる。
窓の規則をその日に当てて計算し直せば、**毎日折れる線**になる。

- **単位はゴールの単位のまま。** 棒（その日の実数）とは別の系列なので、桁が違うループは `dualAxis` で軸を分ける
- ⚠️ **日ごとの平均や累計を、棒の値から目分量で作らない。** 窓の規則をその日に当てて計算する
  （例: 過去30日の累計＝その日までの累計／直近3日の平均＝その日を含む3日）
- ⚠️ **数え方が変わった日より前は線を引かない。** 別の指標を1本の線でつなぐと、変化に見えるものが数え方の違いになる
- `line` を持たないループは、これまでどおり計測点をつなぐ（`points` の `end` の位置）
- ★ **計測点を行き来するナビ（前へ／次へ）を付けない。** 使われないうえ、過去の点に戻すために
  レポート・ゲージ・棒の切り方まで分岐が増える。**常に最新だけを出す**
- **棒は直近10本まで。** これをやらないと日が経つほど細くなって、いつか読めなくなる
- ★ **縦軸の上端は `max(目標, 実測)`。** 目標で切ると、目標を超えた日がグラフの外に出て消える
- ★ **ただし目標が実測の5倍を超えるときは、この規則が逆に働く。** 上端が目標になるぶん
  **棒が下に潰れて、日ごとの動きが読めなくなる**。そのときは**縦軸をデータに合わせ**（実測の1.15倍）、
  目標は右上に「**↑ 目標 3,300人/日（グラフの外）**」と文字で出す。
  ⚠️ **破線を上端に引かない。**「上端＝目標」に見えて、距離を読みちがえる。
  どれだけ離れているかは**ゲージ（`value / target`）が持っている**ので、グラフは在りかだけ示せばいい。
  ★ 実際に起きた（2026-09-10）。L05 が「いま283人/日・目標3,300人/日」になった瞬間、
  棒が高さ12%まで潰れて、230〜386人の動きがまったく読めなくなった
- ★ **下げたいループ（コスト・エラー率など）は `targetLabel: "上限"` を置く。** 破線のラベルが
  「目標 0.3円/人」から「**上限** 0.3円/人」に変わる。既定は「目標」なので、上げたいループでは何も書かない。
  あわせて**画面の右の数字ブロックのラベルも「目標」→「上限」**にし、ゲージの下は
  「上限の 91% を使っています」のように**使用率として読ませる**（`value / target` の意味が
  「達成率」から「使用率」に変わるだけで、計算は同じ）
- ★ **棒の数字は棒の内側に深く置く。** 棒と線は近い値を通るので、棒のすぐ上に出すと必ず重なる。
  棒が低すぎて入らないときだけ棒の上に出す
- **日ごとの数字を持たないループは、これまでどおり折れ線だけ**にする。無理に作らない
- データは `LOOP_DATA.hist` の `days`（`[{ d, v }]`）と `dayUnit`（棒の数字に付ける単位。`%` `件` `円`）。
  **正は `days`**で、画面のレポートの日ごとの表がその写し
- ★ **途中の日（今日）も棒に入れる。** `{ d, v, partial: true }` と書くと薄い色になる。**それだけ。**
  「途中」の印・注記・「—」を足さない。毎日見る人には薄いだけで分かる
- データは `line`（`[{ d, v }]`）と `days`（`[{ d, v, partial }]`）。**どちらも正は `LOOP_DATA`**。
  レポートの日ごとの表がその写しで、「その日の値」の行が `days`、「折れ線」の行が `line`
- ★ **`line` を html の中で `days` から計算しないこと。** 窓の規則はループごとに違い、
  **棒からは計算できないループがある**（分母が棒に無い／途中で数え方が変わった）。
  ⚠️ 2026-09-09 に「描くときに `days` から計算すれば二重に持たなくて済む」と提案したが、7つのうち3つで成立しなかった。
  **html は表示用。数字の作り方を html に置かない。**
- ⚠️ **数字を更新したら `line` も引き直す。** `days` だけ直して `line` を置き去りにすると、
  棒と線が別々の日を指すことになる
- ⚠️ **線が棒より手前で止まるのが正しいこともある**（窓の外の日・集計途中の日・数え方が変わる前の日）。
  止まっていること自体は誤りの印にならない。**見るのは「いちばん新しい計測点の日が、`line` の最後に入っているか」**
- ⚠️ **`history` の値と `line` の値は、同じ日でも一致しないことがある。これは誤りではない。**
  `history` は**そのとき見えていた値**、`line` は**いまのデータで引き直した値**。
  あとから売れた・外部の集計の反映が遅れて数字が伸びた日はずれる。
  グラフの丸は `line` から打つので画面上は食い違わないが、**その点の `note` に理由を1行書いておく**

### TRIAL

- **`trials` の件数ぶん `.trial` ブロックを並べる。** 1件に限らない。0件なら空の表示
- 右に **ステータス**（`.trial-status`）と **`指示する` ボタン**（`.ins`）を置く
- 本文は **実現手順のチェックリスト**。`<ul class="checks">` に1行1件、頭に `✅`（済）／`⬜`（まだ）を付ける。`LOOP_DATA.trials[].plan` の `✅`/`⬜` をそのまま写す。**TRIAL に移した瞬間から出す**（全部 ⬜ でよい）
- 手順の本文は進行ファイルに置き、最後の1行でそのパスを指す。ここは実装の手順書を読む場所ではない（原理6）

★ **実施が終わっても、TRIAL に「完了」の印を付けない**（原理5）。
  全部 ✅ なら `.trial-status` に「全部済み。直しがなければ『完了にして』」と書いて止まる。**RECORD には作らない。**
  ユーザーが「指示する」→ 札 **「完了にして（評価に移す）」** を送ったら、`SKILL.md`「評価に移す」の手順（効果を確かめるかを聞く）を経て
  その `.trial` を外し（他に無ければ空の表示）、RECORD に1項目作る。完了の印は RECORD の `.record-meta` の `実施済`（完了日つき）だけ。

```html
<div class="trial-name">どこで抜けているかを測れるようにする</div>
<div class="head-right"><button class="ins" …>指示する</button><div class="trial-status">全部済み。直しがなければ『完了にして』</div></div>
```

★ **`指示する` があることが TRIAL の役割。** 完了にして・実現方法を選ぶ・別案を出す・やめる、を全部ここから出す。
**押すたびに実装が走る場所ではない。** 決めるための入口。

```html
<div class="trial">
  <div class="trial-top">
    <div class="trial-name">ゲームバナーの上にロック解除ボタンを置く</div>
    <div class="head-right">
      <button class="ins" data-id="L01" data-loop="…" data-text="…">指示する</button>
      <div class="trial-status">実現方法を決めるところ</div>
    </div>
  </div>
  <div class="todo"><ul class="checks"><li>⬜ 1. 実現方法を決める</li><li>⬜ 2. …</li></ul></div>
</div>
```

### ★ 塊で見せない（`SKILL.md`「一目で終わりが見えない塊は読まれない」の画面側）

- 各ブロックは **結論1文（`.lede`）＋補足1行（`.sub-lede`）**。それ以上は `<details class="fold">` に畳む
- 数列は `.dtbl`（小さい表）か棒（`.rv-h`）に。文章の中に「／」でつないだ数字を置かない
- 施策案は見出し（動詞で終える）と根拠（`.why`・小さく1行）を分ける
- 太字はブロックに1つ。`<p>` の中に `<details>` を入れない（`<div>` にする）

### ★ 薄い補足文を画面に置かない

**仕組みの説明を、薄い小さな文字で画面に添えない。全部ノイズ。**
セクションの下の「効いた・効かなかったの判定だけでなく…」
「計測が1回だけなので、まだ線になりません」「この画面は AI が更新しています」——
**どれも読む人には要らない。** 仕組みは `SKILL.md` にあれば足りる。

★ **薄い色の補足文字はノイズにしかならない。** 読ませたい文なら濃く書き、読ませないなら置かない。

置いてよいのは**中身のある文**だけ。「場面は1試合につき1回しか数えない」「9月5日ごろに、もう一度見ます」のような、
**数字の読み方や次の予定**は残す。判断は「**これが無いと数字を読み違えるか**」の1問。

### 棒グラフ（日ごと）の単位

**棒は「その日の実額」で描く。** ゴールが月額でも、棒を月換算にしない。
`6470円` のような**実在しない額**が並ぶと、何を見ているのか分からなくなる。

ゴールと単位が違うときは、**目標線と折れ線のほうを1日ぶんに直す**。

```js
dayTarget: 167, dayTargetUnit: "円/日",   //=== 月5,000円 ÷ 30
days: [ { d:"9/4", v:57 } ],              //=== その日の実額
points: [ { value: 1940, dayValue: 64.7, … } ]  //=== 大きい数字は月額、線は1日あたり
```

★ **勝手に換算しない。** 1日ごとの値を見たい場所で月間に直すと、元の数字が読めなくなる。

### レポート（GOAL の中）

`.hist` の中、**折れ線（`.hist-chart`）と記録の囲み（`.hist-recs`）のあいだ**に置く。

```html
<div class="hist-report">
  <div class="hr-title">レポート <span class="hr-when">窓 8/29〜9/3（6日・本番のみ）</span></div>
  <div class="split"> … 既存の2列をそのまま使う … </div>
</div>
```

- **既存の部品を使う。** `.split` / `.split-row`（名前／補足／数字）やファネルの使い回しで足りることが多い。
  ただし**形は目標ごとに違う**ので、列数や表の作りは決め打ちしない。**その数字を読むのに必要な形**にする
- 窓（いつからいつまでの数字か）は `.hr-when` に必ず書く。**これが無いと、いつの数字か分からない**

### グラフ下の出来事は5行まで

`LOOP_DATA.hist` の `recs` / `after` は LOG から生成する出来事の要点。各囲み5行まで。
「前の計測〜この計測」の範囲で、本番変更・外部の出来事・計測の問題など数字を読むのに必要なものを選ぶ。
最新の点だけ、その計測後の出来事を `after` に出す。RECORD の現在評価を過去の区間へ流し込まない。
LOG 全文は HTML に複製しない。必要なときに見に行ける相対リンク `logs/<ID>.md` を置く。

### RECORD — 施策の評価

見出しは **RECORD / 施策の評価**。日付ごとの `.rec-row` の羅列を、施策ごとの `.record-item` に置き換える。
施策名、実施日、現在評価と評価日、比較した数字・期間・母数、判断の限界がひとまとまりで読めるようにする。
**施策の効果と現在の評価がひと目で伝わるようにする。** 重要な数字は強調し、単位・期間・比較対象も近くに示す。
経緯や関係性は、図や時系列にすると理解しやすい場合に視覚化する。補足は必要に応じて折りたたむ。
強調した観測値がそのまま施策の効果だと誤解されないよう、効果が未確認ならその評価も数字の近くに見えるようにする。判断に必要な限界は折りたたみの中だけに隠さない。
レイアウトや図の種類は固定せず、内容に合わせて選ぶ。テンプレートは参考例であり、同じ配置や必須フィールドの羅列に当てはめない。

- 現在の評価を先に読めるようにし、根拠を続ける。**評価の文（`.rvd-body`）は 100 字以下**（`check-text.py` と同じ上限）、それ以上は本文へ。評価待ちは理由を添える。
- 「測らない」を段階の位置に出さない。計測を入れる施策は計測が走れば A。売上への効果は本文に「測っていない」と書く
- AI の暫定評価とユーザー確定判定を区別する。確定判定は判定日とともに残し、現在評価と違っても消さない。
- 実施した施策には `実施済` と完了日を残す。効果を確かめない決定（A〜E は付ける）や、方針未記録も本文で読めるようにする。
- 施策ごとのコメントはループID・施策名を指示文に入れる。右のチャットへ送る仕組みは共通の入力の窓（アプリが出す）を使う。
- **各項目の評価日を常に表示する。** いつ時点の評価かが分からないと、根拠と評価がずれて読まれる。
- 評価を更新しても施策は同じ項目。履歴の羅列を増やさない。判断の大きな変更だけ LOG へ残す。
- 空なら「まだ実施済みの施策はありません」。外の出来事や気づきで埋めない。

### セクションの見出し

**セクションの上端に4pxの色線をセクション幅いっぱいに引き、その線の直下・左端に台形のタブを置く。**
タブには**英字と日本語の両方**を入れ、これが見出しを兼ねる（下に大きな見出しを重ねて置かない）。

| | GOAL | BOTTLENECK | TRIAL | RECORD | 一覧 |
|---|---|---|---|---|---|
| 線 | `#3f5a72` | `#9b6518` | `#52751f` | `#46534b` | `#74827a` |
| タブの地 | `#eaeff4` | `#f7efe2` | `#eef4e4` | `#eef1ec` | `#eef1ec` |
| 文字 | `#33495c` | `#7d5214` | `#3f5c17` | `#2c3a32` | `#3f4b44` |

- **色はセクションごとに固定する。** ループを行き来しても同じ色が同じ意味になる
- 台形は `clip-path`。⚠️ **`clip-path` と `filter` を同じ要素に置くと影が切られて消える**ので、形は `::before`、影は本体に分ける
- ⚠️ **文字は `line-height:1` で揃える。** 行送りが違うと英字だけ上にずれる
- **GOAL だけはループ名を大見出しとしてタブの下に残す**（ループ名は長く、タブに入らない）。
  「← ループ一覧」はカードの外・上に出す（線とタブのあいだに挟むと、タブがどの線のものか分からなくなる）
- ★ **見出しを大きくするだけでは「章立て」に見えて、どこからどこまでが1セクションか分からない。** 範囲が見える形にする。

### 施策案の行

**左に `💡施策 N` の緑ピル**（地 `--good`・枠 `#54604d`・白抜き・幅96px）。番号は残す。
★ **番号があるので、ボタンを押さず「L01の2番やって」と打っても通る。**

### 出来事のLOG

**タイトルそのものを `logs/L01.md` へのリンクにし、別タブで開く**（2.3.4 から。頁の中には広げない）。

```html
<p class="record-log"><a href="logs/L01.md" target="_blank" rel="noopener">出来事のLOG<span class="arw">↗</span></a></p>
```

- ブラウザでは別タブ、アプリでは別ウィンドウで開く。`.md` はそのままテキストで出る（装飾なし・ダウンロードにならない）
- 畳んだループの LOG（「畳む前の L02 の出来事」など）も同じ形で、行き先だけ変える
- ⛔ `<details>` と `<iframe>` で頁の中に広げない（2.3.3 までの形）。⛔ `fetch` で読まない（`file://` では CORS で弾かれる）

### 1施策の並び

**評価 → 図 → ⚠️限界** の順。全施策で揃える。

```html
<article class="record-item" id="record-L01-T01">
  <div class="record-top"><h3>ゲーム枠の上にロック解除ボタンを置く</h3></div>
  <p class="record-meta">実施 2026-09-02 · 実施済 · AI暫定評価 2026-09-06 19:15</p>

  <div class="record-verdict">
    <div class="rvd-score"><b>C</b><i>半分</i></div>
    <div class="rvd-body"><span class="rvd-k">現在の評価</span><p>呼ばれる回数は増えた。ただし売上は動いていない。</p></div>
  </div>

  <div class="record-viz">… CSSの棒だけで描いた図 …</div>
  <p class="record-warn">⚠️ 同じ日に別の変更も入っており、切り分けられていない。</p>
  <button class="cmt record-comment" …>この施策にコメント</button>
</article>
```

★ **評価は図より前に置く。** 図を先に出すと、数字が施策の効果に見える。

### 変更・狙い・次に見るは画面に置かない

**「変更」「次に見る」は操作する側の材料**で、画面を見る人は使わない。`records[]` にあれば足りる。
折りたたみに入れて画面へ持ち込まない。

★ **ただし「事前の予想」と「判定日」は画面に出す。**
判定の場で予想が手元に無いと、**後から数字を見て「効いた」と言えてしまう**。
評価カードのすぐ下に1行で出し、**無いときは「予想 未記録」と書く**（無いことも判定の材料なので隠さない）。
効果を確かめないと決めた施策は、「予想」の行に「効果は測っていない」と書く。

```html
<p class="record-forecast"><span>予想</span>2週間で 7件 → 10件<em>判定 9/16</em></p>
<p class="record-forecast none"><span>予想</span>未記録</p>
```

### 評価の見せ方

**`A / B / C / D / E / -` の5段階を、濃い地に白抜きで左に置く。**
段階の下に意味を1語（狙いどおり／おおむね／半分／わずか／届かず／未評価）添え、**凡例を別に置かない**。

| | A | B | C | D | E | - |
|---|---|---|---|---|---|---|
| 地 | `#4a6b1c` | `#6b8536` | `#9b6518` | `#a9522c` | `#a8443a` | `#e6eae2` |
| 字 | 白 | 白 | 白 | 白 | 白 | `--dim` |

**A（緑）から E（赤）へ寄せ、明るさは揃える。** 1つだけ目立つ色にしない。
**`-`（未評価）だけ薄い地に濃い字**にして、まだ評価が付いていないことを色で分ける。

- ⚠️ **点数（n/10）にしない。** 細かい点差に意味を持たせられず、分母の説明も要る
- ⚠️ **A〜E は薄くしない。** 薄いと、そもそも目に入らない
- ⚠️ **右上にステータスピルを置かない。** `実施済` は実施日の行（`.record-meta`）に書く
- ★ **評価は薄いと目に入らない。** 濃い地に白抜きで置く。**記号ひとつでは意味が伝わらない**ので、必ず言葉（狙いどおり／半分…）を添える。

### 図は CSS の棒だけで描く

**JS も D3 も使わない。** 幅が変わっても崩れず、`LOOP_REDRAWS` への配線が要らない。
縦棒（日ごとの推移＋実施日の印）と横棒（前後・内訳の対比）の2つで足りることが多い。

- **実施日の棒に印を付ける**（`.rv-col.on`＋ラベルを `--warn`）。前後がその場で読める
- **数え方が変わった区間・条件が違う区間は斜線**（`.rv-col.alt`）にして、同じ色で並べない
- 図の下に1〜2行で、**実施前 → 実施後**を単位つきで書く
- ⚠️ **強調した数字がそのまま効果に見えないよう、限界を図のすぐ下に出す。** 折りたたみに入れない

ラベルは既存の `.rec-v` のピルを使う。評価待ちや不明は `warn`、明示的な改善の評価は `good`、悪化は `bad`。
色は表示上の補助で、`LOOP_DATA` に状態 enum として保存しない。評価は A〜E 以外に無いので、`todo` のような別ラベルを作らない。
グラフを持たないループでも、施策の評価日と実施日は表示する。

### コメント

全セクション見出しに付ける。押すとアプリが入力の窓を出し、入力して「送る」で指示文が右のチャットへ送られる。
窓の操作（Esc・背景クリック・キャンセル・`⌘/Ctrl + Enter`）はアプリが持つ。

プレースホルダは **「このセクションへのフィードバックをどうぞ。」**

### 指示する

**ボトルネックの各行に置く。** 押すとアプリの入力の窓が開き、入力した内容がそのまま指示になる。

- 送られる指示文: 上の「指示文の形」の YAML ブロック（`section: BOTTLENECK`・`target:` に項目テキスト・`feedback:` に入力）
- プレースホルダは **「これを TRIAL に移して手順を出して（実装はしない）／これは消して／この認識は違う、など。そのままどうぞ。」**

★ **`やる` という決め打ちのボタンにしない。** 拾い上げるとは限らない。
**消したい・認識が違う・後回しにしたい**も同じ入口から出せるほうがいい。

★ 入力の窓はコメントと共有し、キッカー（`COMMENT` / `INSTRUCTION`）で見分ける。
文言の組み立ては `compose` 関数を差し替える形にしてあるので、**用途が増えても分岐が増えない**。

★ **入力の窓はアプリが出す。殻には置かない**（2.3.0 で殻から `#modal` を外した）。殻が決めるのは「何を聞くか」と指示文の組み立てだけ。
アプリとの約束（変えない）:

```js
window.rlaApp.ask({ kick, title, sub, placeholder, chips, value })  //=== → 入力された文（キャンセルなら null）。chips は [[札の文字, 入れる文], …]、value は最初から入れておく文
window.rlaApp.send(指示文)                                    //=== 指示文をアプリへ直接渡す（クリップボードは使わない）
```

- **定型の札**を本文の下に置く。押すと本文に入るだけで、送信はしない。**キッカーが `INSTRUCTION` のときだけ出す**（コメントには出さない）。
  札は `rlaApp.ask` の `chips` で渡す。施策案（`.do`）は `TRIAL に移す`（本文は `これを TRIAL に移して手順を出して（実装はしない）`）/ `これは消して` / `この認識は違う`、
  TRIAL（`.ins`）は **`完了にして（評価に移す）`** / `これは消して` / `この認識は違う`。**「完了にして」は TRIAL にしか出さない**
- ボタンの見た目は **📋 付きの破線の札**。押すと指示文が右のチャットへ送られ、AI が動く

### ★ ボタンは「見るだけの画面」の一部。押したら右のチャットへ送る

画面そのものは **見るだけの紙** で、ボタンは **指示文を作る** だけ。作った指示文は `rlaApp.send` でアプリに渡し、アプリが右のチャットへ送って AI が動く。
💡 のコマンドなど、指示文でないコピーだけはクリップボードへ書く。

- 送り先の右の窓が閉じていれば、アプリが開く。殻は何もしない

### この画面の使い方・右の窓の開閉・版の表示

アプリのタブの列（［? 使い方］［AI の窓］・設定）にある。**殻にも頁にも置かない**（2.1.0 で殻から外した）。
殻に残すのは、見えない版の表示 `<span class="ver" hidden>v<版></span>` だけ（アプリが版の判定に使う。作るときは雛形のまま、版はアプリの入れ替えが書く）。

### 右の窓（AI のチャット）

**アプリが自分の窓として、ループの画面の右に並べる。殻にも頁にも置かない**（2.2.0 で殻から外した）。
画面（HTML）は窓の幅を空けない・開閉を知らない。窓を開くとアプリがループの画面ごと狭めるので、`resize` が飛ぶ。

アプリとの約束（変えない）:

```js
//=== 殻の CONST ブロック
var PROJECT_DIR = '/絶対パス/プロジェクト';   //=== loops/ の親の絶対パス
var PANES = ['s-list','s-L01','s-L02'];      //=== チャットを付ける画面IDの一覧。アプリが読む。セッションIDはここに持たない
```

- アプリは殻の hash（`#s-list` / `#s-L01`）で、いまの画面を知る。`PANES` に無い画面は一覧のチャットにする
- `PANES` に無いループには、そのループのチャットが付かない。ループを足したら `PANES` にも足す
- 殻の CONST ブロックの `var PROJECT_DIR` に **`loops/` の親の絶対パス**を書く。
  ★ **雛形のまま置かない**（雛形は `'/絶対パス/プロジェクト'` というプレースホルダ）。Windows のパスも `/` 区切りで書く（例: `'C:/Users/…/proj'`）
- 道具（claude / codex）はアプリで選ぶ。画面側に切替は無い
- セッションIDはアプリ側が持つ。昔の `loops/.chat-sessions` はアプリが読むだけ。**消さない**

★ **送信はアプリがやる。** ボタンが書いた指示文をアプリが受け取り、右のチャットに貼り付けて Enter まで押す。
画面（HTML）は入力を受けないまま。「HTMLは見る専用」は崩さない。

## ★ 実寸で描く図は、描き直しをつながないと壊れる

折れ線もファネルも **`clientWidth` を見て実寸で描く**。つまり**幅が変わったら描き直す必要がある**。
描き直しは `window.LOOP_REDRAWS` に関数を積んでおき、次の2つから呼ぶ。

| きっかけ | なぜ必要か |
|---|---|
| `show()`（画面の切り替え） | **隠れている画面は幅が0**。初回の描画では何も描けていない |
| `resize` | 窓の大きさが変わる。連続で来るので間引く |

右の窓の開閉は、アプリがループの画面ごと幅を変えるので `resize` で描き直される（2.2.0 より前は殻の中の余白が変わるだけで `resize` が飛ばず、**枠474pxにSVG794px**がはみ出したまま残った）。

## ★ 図は部品を呼ぶ。手で SVG を描かない

**頁に書くのは1行だけ。** `rising.js` が `data-rl` を読んで中身を組み立てる。

```html
<div class="rl" data-rl='{"t":"bullet","unit":"円","max":24,"now":1.37,"aim":24,"was":3.46,"wasLabel":"はじめた頃"}'></div>
```

★ **同じ絵を2回描かない。** 1.6.x では、見本の頁・ループ頁・`rising.js` に
**3種類のファネル**が生えていた（横向きの台形／縦に細くなる台形／中央寄せの横棒）。
どれも同じものを描いていて、直す場所が3つに増えていた。
**「その場で描いたほうが速い」は、次の版で必ず跳ね返る。**

★ **部品に無い形のときだけ、その場で描いてよい。** 描いたものが2回目に出てきたら、
そのとき部品に昇格させる（`rising.css` と `rising.js` に足して、`data-rl` から呼ぶ）。

### どれを使うか — データの形で決まる

★ **表を引く前に、その施策の「見る数字」を1つ決める。** 頁の `.rv-title` に
`見る数字・GA4` のように書いてある、**その施策が自分を証明／反証する数字**のこと。
**表はその1つの数字の形に対して引く。** 施策が持っている数字ぜんぶに対して引かない。

★ これを飛ばすと**全部 `bullet` になる**。施策はどれも「予想」を持っているので、
「いまと目標が同じ単位で並ぶ」は文字どおりほぼ全件に当たってしまう。
見る数字を先に決めれば、券の内訳を見る施策は `rank`、入口ごとの前後を見る施策は `dumbbell` に落ちる。

**AI のセンスで選ばない。上から順に見て、最初に当てはまったものを使う。**

| データの形 | `t` | 図 |
|---|---|---|
| **日付ごとの数字が並ぶ**（3日以上） | `data-hist` ／ `cal` ／ `hist` | 折れ線・棒＋線2軸／カレンダー／縦棒 |
| **段を追うごとに減っていく**（桁が変わるほど減る） | `funnel` | ファネル |
| 率が1%未満。または**母数が100未満**で実数を読ませたい | `donut` | 粒（ドーナツ） |
| **項目ごと**（種類・入口・期間）の数や率が並ぶ | `rank` | 横棒ランキング |
| 2件以上の項目に、それぞれ前といまがある | `dumbbell` | ダンベル |
| 全体を2つ以上に分ける。**期間を並べて比べる** | `stack` | 帯100% |
| 内訳で最大と最小が10倍以上ちがう | `treemap` | ツリーマップ |
| 全体を2〜5に分ける。割合を見せたい | `pie` | 円 |
| 2時点だけ。項目が3つ以上 | `slope` | 傾き |
| 曜日や日付のクセを見たい | `cal` | カレンダー |
| 合計の推移と、その内訳を同時に | `area` | 面グラフ |
| ばらつきを見たい（区間ごとの件数） | `hist` | ヒストグラム（縦棒） |
| 2つの集まりの重なり | `venn` | ベン図 |
| 1件ずつの生データが2列ある | `scatter` | 散布図 |
| **上のどれにも当たらず**、いまと目標が同じ単位で並ぶ | `bullet` | 軸つきブレット |
| **数字が取れなかった・測るのをやめた** | — | **図は置かない。一言だけ書く** |

★ **`rank` の条件に「0件がある」は要らない。** 0件があっても行が消えないのは `rank` だけ、
というのは**利点の説明**であって条件ではない。必須と読むと、0件の無い期間比較が
`bullet` まで落ちてしまう（3人が同じ場所でつまずいた）。

★ **畳んだ中にも実寸の図（`funnel`・`data-hist` の折れ線）を置いてよい。**
1.7.0 で「折りたたみを開いたら描き直す」を足した。それ以前は幅が0のまま描かれず、
開いても空のままだった。

★ **段数でファネルを選ばない。** 「3段だから待ち行列」ではない。
2,099 → 1,037 → 209 は3段でも10倍減るのでファネル。**減り方で選ぶ。**

★ **`waffle`（100マス）と `queue`（待ち行列）は 1.7.0 で廃止した。**
`waffle` は母数が100でないとマスが実数とずれる（4回を7マス塗ってしまった）。割合は `pie` か `donut`。
`queue` は減り方が見えないので `funnel` に寄せた。

★ **`bullet` は受け皿。いちばん下にあるのは意図的**。条件が広いので、上に置くと他が全部埋もれる。

### 図を置く場所 — ゴールと施策だけではない

★ **数字が3つ以上並んでいる場所は、すべて図の置き場所。** セクションで切らない。

| 場所 | よくある形 | 置く図 |
|---|---|---|
| GOAL の達成度 | いま・目標・はじめた頃 | `bullet` |
| GOAL の**レポート** | 日ごとの一覧・枠ごとの数字・期間の比較 | `data-hist` ／ `cal` ／ `rank` ／ `stack` |
| BOTTLENECK | 段ごとに減る人数 | `funnel` |
| 施策の**観測枠** | 見る数字の前後・内訳 | 引き金の表で決める |
| 施策の**足元**（`.rv-foot`）と根拠 | 日ごとの実績・内訳 | 図にするか、折りたたみへ |

★ **レポートを「範囲外」にしない。** 1.7.0 の実測では、ゴールと施策だけを直した結果、
レポートに日ごとの数列が20〜25件残った。**いちばん醜い塊はそこにある。**

★ **数列を「短くする」と、もっと悪くなる。** 100字に収めようとして
`1,166 → 767 → 531 → 302 …` に詰めると、検査の長さは通るが読めない。
**日ごとの数字は図に移す。文に残さない。**

- **施策1件に図は1つ。** 2つ置くと、どちらを見ればいいか分からなくなる。
  観測枠が2つ以上ある施策は、主でないほうを `<details class="fold">` の中へ**移す**（消さない）
- **図を1つにしたら、`.rv-title` の文言もその図に合わせる。** 枠と要素は残したまま、題だけ詰める
  （例: 「見る数字　ホスト1人あたりの手取り…と 券ごとの件数」→「券ごとに、払った件数（台帳の sku）」）
- `rank` と `hist` は、1.3.x からある `.rv-h` と `.rv-bars` をそのまま出す（見た目は増やしていない）
- **0件を見せたいときは `rank` だけ。** `treemap` と `stack` は面積が0になって行ごと消える

### 但し書きは、見える3行に何を残すか

観測枠の足元（`.rv-foot`）に置けるのは3項目まで。**あふれたら折りたたみへ移す**（消さない。
`SKILL.md` の「削除ではなく移動」は**既存の頁を直すときも同じ**）。残す順はこう決める。

1. **いまの判定を変えうるもの。** 母数が小さい／別の施策と期間が重なっている／比べる相手がいない
2. **数字が揺れるもの。** 集計が途中／取り漏れがある／取得の時点が古い
3. それ以外（変更の中身・狙い・次に見るもの・生データ・通算）は**折りたたみへ**

★ 「狙い」「変えた中身」は**画面に置かない**。書いた本人しか読まないうえ、判定には使わない。
消さずに畳む。

### 書き方の決まり

- `data-rl` は **JSON**。シングルクォートで囲み、中は必ずダブルクォート

★ **ブレットの色は決まっている。はじめより悪くなっていたら赤、それ以外は緑。**
`was`（はじめ）と `now`（いま）を比べて部品が塗る。**`ok` を書いて塗り分けない。**

| 目標の種類 | 赤になるとき | 書き方 |
|---|---|---|
| 上げたい（売上・人数・率） | いまが**はじめより下** | そのまま |
| 上限（サーバー代・コスト） | いまが**はじめより上** | `"aimLabel":"上限"` か `"lower":true` |
| はじめが無い | 塗らない（中立の灰色） | 向きが分からないので判断しない |

★ **「目標に届いていない」で赤にしない。** ほとんどの目標は届いていないので、全部が赤になり、
**本当に悪くなったものが埋もれる**。1.7.3 までは `ok` を書かないと全部赤だった
（上がっている T09・T03 も赤で、下がっているゴールと見分けがつかなかった）。
一覧の行の左の帯も同じ決まりで塗る。**帯・数字・ブレットの色が揃う**。

★ `ok:true` / `ok:false` は決まりに当てはまらない例外のときだけ書く（書いたほうが勝つ）。

★ **数字を焼き込まない。`LOOP_DATA` から引く。** 値に `"@hist.target"` のように書くと、
`rising.js` が描くたびに `LOOP_DATA` を見にいく。**焼き込むと次の計測で、上の大きい数字と
下の図が別のことを言う**（1.7.0 で実際に起きた。6頁すべてが対象だった）。

| 書き方 | 引くもの |
|---|---|
| `"@hist.target"` | 目標 |
| `"@hist.unit"` | 単位 |
| `"@metric.start"` | はじめた頃 |
| `"@hist.points.last.value"` | いちばん新しい計測の値 |
| `"@hist.days[]"` | 日ごとの配列そのもの（`rank` `hist` `cal` にそのまま渡せる） |
| `"@hist.days[].v"` | 日ごとの値だけを集めた配列 |

```html
<!-- ゴールの帯。数字は1つも書かない -->
<div class="rl" data-rl='{"t":"bullet","unit":"@hist.unit","max":"@hist.target",
  "now":"@hist.points.last.value","aim":"@hist.target","was":"@metric.start","lg":false}'></div>
```

★ **引けなかったときは `@…` の文字がそのまま出る。** 黙って空にしない。綴りの間違いに気づける。
★ `LOOP_DATA` に無い数字（別ループの値・その場で計算した割合）は、これまでどおり直に書く。
  そのぶんは**更新のたびに自分で直す**ことになるので、`update/LXX.py` にも差し替えを足す

★ **図を足したら `update/LXX.py` にも差し替えを足す。** 忘れると、次の「更新」で
`LOOP_DATA` の値だけ新しくなり、**図の中の数字が古いまま残る**。
1.7.0 の実測では、6ループに58個の図を置いたのに、更新スクリプトは1本も `data-rl` を知らなかった。

```python
# loops/update/L01.py の末尾に足す例（common.py の load/save は LOOP_DATA しか見ない）
import json, re
def set_rl(html, i, **kv):
    """i 番目の data-rl の値だけ差し替える。構造は変えない"""
    ms = list(re.finditer(r"data-rl='(\{.*?\})'", html))
    d = json.loads(ms[i].group(1)); d.update(kv)
    new = json.dumps(d, ensure_ascii=False, separators=(',', ':'))
    return html[:ms[i].start(1)] + new + html[ms[i].end(1):]
```

★ **図が何番目かは動く。** 頁の構造を変えたら番号もずれるので、
スクリプト側では `data-rl` の中の `title` で探すほうが安全
- 一覧を渡す図（`rank` `stack` …）で中身が空なら「まだ数字がありません」が出る。**空の箱は出ない**
- 単位やラベルは `esc` を通るので、`<` や `"` が入っても markup は壊れない
- ゴールの枠のように、いまと目標が図の左右に大きく出ている場所では **`"lg":false`** で凡例を消す。
  同じ数字を2回言わない
- d3 は `loop.html` が必ず読む。**d3 が無いときの逃げ道は持たない**

## ★ 計測点の「入ったこと」は、大事な順に書く

`hist.points[].recs` は**放っておくと文字の塊になる**。1回の更新で5〜8行増え、
どれも同じ重さで並ぶので、どれを読めばいいか分からなくなる。`rising.js` 側は2つで防いでいる。

- **日付が全部同じなら列をやめる**（`9/26` が7回並んでも読む役に立たない）
- **先頭2行だけ出して、残りは「ほか N 件」に畳む**

★ **だから順番が意味を持つ。** 畳まれる前提で、この順で書く。

1. **なぜ動いたか。** その計測で数字が動いた理由を1つ。動いていなければ「動いていない」と書く
2. **その数字を信じていいか。** 途中の集計・未払い・取り漏れなど、いまの値が変わりうる事情
3. 以降は日ごとの実績、施策ごとの数字、データの但し書き（畳まれる側）

★ `note` の中の `\n` は改行として出る。1行が長いときはここで割る（`<br>` は文字として出るので使わない）。
`recs` は `innerHTML` なので `<br>` が使える。

## ★ 施策のIDは画面に出す。「完了」は出さない

★ **見出しの先頭に `<span class="tid-pill">T05</span>` を置く。** TRIAL も RECORD も。
一覧が <code>L05</code> を出しているのと同じ。ループは L、施策は T。

★ **理由。** 本文は「T09 が入るまでの4日」と書く。**IDが画面のどこにも無いと、
読む人には何のことか分からない**（プレイルームでは本文のIDが134件あり、指し先が1つも無かった）。
`trials[].id` も `records[].id` も既にあるので、出すだけでよい。

★ **本文の中のIDはリンクにする。** `<a class="tid-ref" href="#record-L01-T09">T09</a>`。
押すとその施策まで飛ぶ。同じ頁の中なので確実に辿れる。

★ **実行中の施策にも飛び先を付ける。** `<div class="trial" id="trial-L06-T03">`。
RECORD の `id="record-…"` と同じ形。実行中の施策を指すリンクは `href="#trial-L06-T03"`。
1.7.3 までは RECORD にしか飛び先が無く、「TRIAL の T03 で直す」の T03 が文字のまま残っていた。
「完了にして」で RECORD へ移したら、リンクも `#record-…` に書き換える。

★ **RECORD に「完了」を出さない。** RECORD は「施策の評価」の節で、ここに入るのは
**完了したものだけ**。全件に付けても1つも区別しない。左の評価枠が「未評価」と言っているのに
見出しが「✓完了」だと、読む人が止まる。**状態は評価枠が言う。見出しは「どの施策か」だけ。**

★ **TRIAL の状態は出す。** こちらは施策ごとに違う（「「外す」に決めた（9/17）。実装は未着手」と
「実現方法を決めるところ」）。RECORD の「完了」とは別物。

★ **移した日付は残す。** 語だけ変える: `完了 2026-09-15（TRIAL から外して観察へ）`
→ **`観察へ 2026-09-15`**（17字短くなる）。

★ **「完了」の言い方が他にあっても、同じ2つに揃える。** 実物には「TODO完了」「実装完了」「完了 日付」（括弧なし）もあった。

| いまの書き方 | 揃えた形 |
|---|---|
| 実施した日の「完了」「TODO完了」「実装完了」 | `実施済 2026-09-05`（見本の `.record-meta` と同じ） |
| TRIAL から外した日の「完了」 | `観察へ 2026-09-15` |
| もとから `実施済` | そのまま |

日付の無い「完了」「TODO完了」は消して、`実施済` だけを残す。

## ★ `loops/.tmp/` は作業場。**中身を読んで判断に使わない**

`.tmp` は**書き捨ての作業場**。ここにあるものは**どれも正ではない**。

| 置かれるもの | 誰が置くか |
|---|---|
| 数字の取得結果（`numbers-<日付>.txt` など） | `update/LXX.py`。その日1回だけ取った生の出力 |
| 一時スクリプト（`_L06-active-users.cjs` など） | `update/LXX.py` が書いて実行する |
| 退避（`LXX-before-update.html`・`index-before-*.html`） | 書き換える道具が、書く前に置く |
| 移行の残り（`LXX.md`・`LXX-merge-report.md`） | 1.5.0 の移行で `merge-md.py` が退避した |

★ **読んで判断に使ってよいのは、自分がその場で書いたものだけ。**
数字を取り直したら `.tmp` の txt を読む。それ以外は読まない。

★ **退避と移行の残りは、絶対に読まない。**
頁の**まるごとの写し**なので `LOOP_DATA` が入っている。
`loops/` を grep すると現行の頁と一緒に出てくるが、**どれも古い**。
実例: プレイルームの `.tmp` には `LOOP_DATA` を持つファイルが 84 個ある
（`L01-before-update.html` だけで10本、1.5.0 で捨てたはずの `L01.md` も6本）。
これを拾って更新すると、**古い数字で頁を書き直す**ことになる。

★ **正はこの3つだけ。** 迷ったら `.tmp` ではなくこちらを見る。

| 何の正か | どこ |
|---|---|
| 値（数字・施策・計測点） | `loops/LXX.html` の `LOOP_DATA` |
| 画面に出る文と図 | `loops/LXX.html` の markup |
| 出来事の記録 | `loops/logs/LXX.md` |

★ **`.tmp` は消してよい。** 作業場なので、いつ消しても更新は動く。
溜まって困ったら丸ごと消す（退避が要るのは直前の1回ぶんだけ）。

## ★ 縛るのは「図の選び方」、縛らないのは「並べ方」

ここは線の引き方を間違えやすい。**2つは別のもの。**

| | 縛る | 例 |
|---|---|---|
| **図の選び方** | **縛る。** 同じデータの形には同じ図を使う（上の引き金の表） | 0件がある内訳なら必ず `rank` |
| **並べ方** | **縛らない。** 列の数・行数・節の順・どこに何を置くか | 表を3列にするか4列にするか |

★ **図を縛る理由。** 選び方を AI に任せると、同じ形のデータが頁ごとに違う絵になる。
読む人は毎回「これは何の図か」から始めることになり、ループをまたいで見比べられない。
**選び方はセンスの問題ではなく、データの形で決まる。**

★ **並べ方を縛らない理由。** 列の数・行数・表の形は**目標ごとに変わる**。
数字の組み合わせはループによって違うのが当たり前で、そこを固定すると
**その数字を読むのに必要な形が作れなくなる**。細かく指示するほど、その目標に合わない形を強いる。

並べ方について規約に書くのは、**役割**（どこに何を置くか）と、
**壊れるとまずいこと**（点と連動して畳む、窓を書く）だけ。

```
--dim:#87918b      薄い
--accent:#ccef67   主ボタン
--good:#52751f  --warn:#9b6518  --bad:#b95448
```

- 幅 `max-width: 880px`
- 枠は **1px フラット**。影は使わない（モーダルだけ例外）
- セクションは横罫で区切る。箱で囲まない
- キッカー（`GOAL` `BOTTLENECK`）は `ui-monospace` ＋ `letter-spacing:.12em`
- 数字も `ui-monospace`。**桁が揃わないと比較できない**
- 進捗バーは `.progress-track` / `.progress-fill`（`width:%` で指定）

### 折りたたみ（`details.fold`）

**見出しは「押せる」と分かる形にする。** 左に `＋` の四角（開くと緑の `－`）、文字は本文と同じくらいの太さ。
小さな三角だけだと押せる気がしない、と実際に言われた（2026-09-23）。見た目は `rising.css` が持つので、頁側は
`<details class="fold"><summary>見出し</summary><div class="fd-b">中身</div></details>` だけ書く。

### 主要な数字（殻のタイトル下・`.rev`）

**必ず置く。消さない。** 一覧を開いた人が最初に見る「このサービスはいまどうか」の数字。

- 形: **大きく1つ**（`.rev-total b`）＋ いつの窓か（`.rev-when`）／内訳を小さく **2〜4個**（`.rev-break`）／いつ時点か・取り方（`.rev-note`）
- **何を置くかは AI が決める。** 決め方の順:
  1. そのサービスの目的にいちばん近い**お金か人数**（売上・利用者数・登録者・申し込み数）
  2. `loops/README.md` の取り方で**毎回取れる**もの（取れない数字を置くと更新のたびに古くなる）
  3. 各ループの GOAL と**重ならない**もの（GOAL は一覧の行に出ている）
- 決めたら、`.rev` の直前の HTML コメントに「なぜこの数字か」を1行残す（次に触る人が別の数字に変えないため）
- 「全ループ更新」のたびに一覧の子がここも取り直す（`SKILL.md`「数字を更新し、施策を再評価する」手順4）
- 取れる数字がまだ無いプロジェクトだけ、`.rev-total` に「まだ取れる数字が無い」と書く。**ブロックを消さない**
- ★ 以前は「複数ループを合算した数字。無ければ消す」だったが、プロジェクトごとの主要な数字に変えた（2026-09-18）。既存の殻で `.rev` が無ければ「合わせて」のときに提案する

### 一覧のステータス

**ループ一覧の各行の右。状態の名前ではなく、施策の「件数」を出す。**

| 出るもの | 数えるもの | 色 |
|---|---|---|
| `施策待ち` | どちらも0件のとき | グレーの輪郭だけ |
| `1 実行中` | **TRIAL にあるもの** | 緑の点 |
| `2 評価中` | **RECORD にあって、TRIAL に残っていないもの** | 琥珀の点 |

★ 施策は TRIAL か RECORD の**どちらか一方**にしかいない（`SKILL.md` の2段階。「完了にして」で移る）。
両方に見えるなら移し忘れなので、数える前に直す。

★ **状態の名前（`試行中` `承認まち` `未着手` のような enum）を作らない**（原理6）。数えた結果だけを出す。
実現方法を決めている途中のものも、全部 ✅ で「完了にして」待ちのものも TRIAL にあるので `実行中` に含まれる。**どこまで進んだかは、ループを開いて `.trial-status` を読む。**

```html
<!-- 0件 -->
<div class="state"><div class="st idle"><span class="st-dot"></span>施策待ち</div></div>

<!-- TRIAL 1件 ＋ 観察中 2件 -->
<div class="state">
  <div class="st run"><span class="st-dot"></span><span class="st-n">1</span><span class="st-lb">実行中</span></div>
  <div class="st rev"><span class="st-dot"></span><span class="st-n">2</span><span class="st-lb">評価中</span></div>
</div>
```

- **色は8pxの点だけに持たせる。** 枠や塗りを足すと、行の罫線やゲージと競って一覧が騒がしくなる
- **数字は 17px の等幅**（ラベルは 11px）。遠目には数字だけが読めればいい
- ステータス列の幅は **100px**。ラベルを増やして幅を広げない

## 空のとき

**一覧が0件のとき**は、目標の例を10個（`SKILL.md`「毎回やること」と同じ文言）を `.loop-ideas` に薄く並べ、
「ループを追加」を押すと札に入る、と1行添える。10個の正は `SKILL.md`。ここに別の文言を作らない。

```html
<div class="loop-ideas">
  <div class="li-head">例えばこんな目標</div>
  <ul>
  <li>申し込みを増やしたい</li>
  <li>見込み客を増やしたい</li>
  <li>翌日また来る人を増やしたい</li>
  <li>有料に切り替える人を増やしたい</li>
  <li>解約を減らしたい</li>
  <li>TOEIC の点を上げたい</li>
  <li>YouTube の登録者を増やしたい</li>
  <li>株の含み益を増やしたい</li>
  <li>体重を落としたい</li>
  <li>貯金を毎月積みたい</li>
  </ul>
  <p>右上の「ループを追加」から送ると、AI が目標の数字と窓を聞いて作ります。</p>
</div>
```

**ループ一覧セクションの右（`.sec-right`、タブと同じ高さ）に「ループを追加」**（`.add-loop`）。上のヘッダ（全ループ更新の横）には置かない。押すとアプリの入力の窓（`INSTRUCTION`）。定型の選択肢は例の10個ぜんぶを小さく並べる（3つに絞らない）。
指示文は `section: LOOPS / task: ループを追加して: <入力>`。

ループが空でも寂しくしない。**何を待っているかを書く。**

```html
<p class="forecast">
  リリースが <strong>8月29日</strong> なので、翌日戻ってきたかどうかを見るには、あと数日かかります。
</p>
```

TRIAL が空なら破線の枠（`.trial.empty`）にして、提案があれば出す。

## 確認

作ったら、アプリで開いている画面を見てもらう（書き終わるとアプリが読み込み直す）。見てほしいのは次のとおり。

1. 一覧 → ループ を**クリックで往復できるか**
2. `指示する` と `コメント` と `更新` で、**指示文が右のチャットに届いて送られるか**
3. **セクションの背景が途中で変わっていないか。** 変わっていたらタグの開閉がずれている（「更新するとき」の検算を回す）
4. 殻の `index.html` に `SESS` が残っていないこと
5. **ループ頁が単体で開ける**（`LXX.html` を直に開いて、断り書きが出て崩れないこと）

RECORD 更新後は、同じ施策が重複しないこと、評価日と根拠が読めること、過去の計測点で現在評価の注意が出ることも確認する。

## LOG の形式（`loops/logs/<ID>.md`）

**出来事の正。md のまま残す**（画面に出るのは `hist.points[].recs` に写した最近の数件だけ）。
frontmatter にループの `id` を付けない。

```markdown
# L01 の出来事

- 2026-09-08 ｜評価変更｜購入ボタン：評価待ち → 誘導は改善傾向・購入増加は未確認。根拠は9/1〜9/7の観測。[現在評価](../L01.html)
- 2026-09-01 14:00 ｜本番変更｜ゲーム枠の上に共通の購入ボタンを置いた。[施策](../L01.html)
```

日付順（新しいものを上）で、同日の前後が評価に関係するなら時刻も残す。
普段は前回評価以降の範囲と必要な過去の根拠だけ読む。無変化の再確認・細かい編集・チャットの経過は足さない。
評価の変更履歴は、判断が大きく変わったときの変更前後と理由だけ。ユーザーの確定判定は `records[].verdict` に日付付きで保持し、LOG にも残す。

**LOG 全文をループ頁に複製しない。**

## 評価を更新するとき

同じ施策の観測（markup）・現在評価（`records[].grade`）・評価日（`graded`）を更新する。
**事前予想（`forecast`）やユーザーの確定判定（`verdict`）を書き換えない。**
計測未着なら `grade` を `-` にし、「評価待ち：実施後の数字が未着。次回は…」と本文に書く。実施完了とは別に扱う。
確定判定後に違う証拠が出たら、確定時の判定を残したまま現在評価に違いを書く。変化を LOG に1件残す。
TRIAL に別の施策が並んでいても、過去施策の評価は更新できる。現在の TRIAL の状態には触れない。

## 新規に `loops/` を作るとき

1. `loops/README.md` を作る（数字の取り方を聞いて書く）
2. 目標を1つ決めて `L01.html` を作る（`../assets/loop.html` から。`LOOP_DATA` と散文）。**最初から複数作らない**
3. 残りの画面を揃える
   - 殻 `index.html` ← `../assets/index.html`（CONST の `PROJECT_DIR` `SERVICE_NAME` `PANES` と LOOPS の一覧を埋める）
   - 共通 `rising.css` `rising.js` ← `../assets/` からそのままコピー。独自の見た目が要れば `project.css`（無くてもよい）
4. **右のチャットのために。** 殻 `index.html` の CONST ブロックの `PROJECT_DIR` に、このプロジェクトの絶対パス
   （`loops/` の親）を書く。Windows のパスも `/` 区切りで書く。
   ★ **雛形のままにしない**（書き換えないと、別のプロジェクトのチャットにつながる）。
   **セッションは作らない。** 右のチャットはアプリが出す（上の「右の窓（AI のチャット）」）

**最初のループは、いま一番気になっている数字で作る。** 網羅しようとしない。増やすのはいつでもできる。
